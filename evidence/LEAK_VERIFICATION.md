# IOCP 채팅서버 — 메모리 / 리소스 누수 검증

> **요약:** 동접 약 1,000(피크 1,500) + 접속·해제를 끊임없이 반복하는 부하 + 변조 트래픽 환경에서 **2시간 동안 끊김 없이 부하를 유지**.
> 메모리(Private Bytes)·핸들·스레드 모두 우상향 추세 없음(정상상태 변동 0.4%),
> CRT 힙 델타 분석에서 **51만 connect/disconnect 사이클에 비례하는 누수 미관측**.

---

## 배경 — 누수 추적 맥락

이 검증의 직접 대상은 **PlayerMap 누수**다.

- **발견**: 다중 봇 부하 중 서버 `players` 맵이 계속 증가(세션은 끊겼는데 맵에서 안 빠짐)
- **진단**: `Join`·`Leave` 호출 횟수를 각각 세는 카운터 + `Alive(=Join−Leave)` vs `PlayerMap(=players.size())` 비교로 누수 경로 확정
- **원인**: `CLanServer.cpp` PostRecv/FlushSend의 `SOCKET_ERROR && WSAGetLastError != WSA_IO_PENDING` 즉시 실패 분기에서 `IORelease`만 호출하고 `CloseSession` 누락 → RefCount 짝은 맞아 세션 풀은 반환되나 `OnClientLeave` 미호출 → `players` 맵에서 안 빠짐 (객체 수명 vs 비즈니스 통보 두 축 분리)
- **수정**: 두 분기에 `CloseSession(idx)` 추가 → 봇 종료 후 `Alive=0` 도달 확인 (1000 동접 30분 안정)

이 문서는 그 수정이 **장시간(2h · 51만 사이클)에도 재발하지 않음**을 입증하는 마지막 단계입니다.

---

## 테스트 환경

| 항목 | 값 |
|---|---|
| 서버 | IOCP 채팅서버 (myIOCP), Windows |
| 부하 생성기 | DummyClient `--auto N` (멀티스레드 봇) |
| 부하 패턴 | connect → login → enter room → chat(10~109회) → leave → disconnect 무한 반복 |
| 동접 | ~1,000 (변동 800~1,500) |
| 변조 트래픽 | 5% (패킷 변조 → 서버 MAC 검증 실패 → 강제 종료 → 재접속, 비정상 종료 경로까지 커버) |
| 측정 머신 | i5-13600KF (20 logical cores) |
| 네트워크 | loopback (127.0.0.1) — *누수 검증 목적. 성능 수치 아님* |
| 수집 도구 | Windows Performance Counter (`logman`) + Debug CRT Heap (`_CrtMemDifference`) |

## 검증 1 — 메모리 (Private Bytes)

![메모리 2시간 추세](soak2_private_bytes_2h.png)

- 초기 약 4분: 278 → 403 MB **워밍업** (동접이 차오르며 세션/버퍼 풀 1회 확장)
- 이후 정상상태 약 2시간: **401.4 – 403.1 MB, 변동폭 1.64 MB (0.4%)** → 사실상 평탄
- 1,513 샘플 (5초 간격, 약 2시간 6분)
- 엄밀히는 정상상태도 401.6 → 403.1 MB로 미세 단조증가(0.4%) — 동접 피크(1,500) 시 세션 풀의 high-water-mark가 한 번씩 늘고 미반환되는 패턴이며, **connect/disconnect 사이클에 비례하는 누수와는 다름**(검증 3에서 교차 확인)

**→ 장시간 접속·해제를 반복해도 메모리가 사이클 비례로 우상향하지 않음.**

## 검증 3 — CRT 힙 델타 (바이트 단위 정밀 측정)

Debug CRT(`_CrtMemDifference`)로 시작/끝 힙 스냅샷 비교. 원본: [`crt_heap_delta.txt`](crt_heap_delta.txt)

| 측정 | 기준선(s1) | 잔존 델타 | 누적 할당 | 델타/누적 |
|---|---|---|---|---|
| 1차 | 부하 전(풀 0) | 17.9 MB (22,760블록) | 3.8 GB | 0.5% |
| 2차 | **워밍업 후(풀 확장됨)** | **2.15 MB (686블록)** | 17.3 GB (51만 사이클) | **0.012%** |

- 1차 17.9MB의 대부분(~15.7MB)은 **세션/버퍼 풀 1회 확장분** → 기준선을 워밍업 후로 옮기니 소멸
- 2차 잔여 2.15MB는 누적 17.3GB의 0.012%, 686블록으로 **사이클 수(51만)에 비례하지 않음** → 풀 추가확장/static 잔량

**→ connect/disconnect 사이클당 메모리 누수 패턴 미관측.**

## 종합

| 증거 | 결과 |
|---|---|
| Private Bytes (정상상태 2h) | 변동 0.4% |
| Handle / Thread (2h) | 우상향 없음 |
| CRT 힙 델타 (51만 사이클) | 0.012%, 사이클 비례 아님 |

세 측정이 일관되게 **장시간 부하에서 메모리·자원 누수 미관측**을 가리킴.

> **CPU(참고용):** 서버 프로세스 `% Processor Time`은 정상상태 평균 **0.61코어(20코어의 3.0%)**, 피크 1.48코어(7.4%) — 1코어 미만. 단 loopback에서 서버와 부하기가 같은 CPU를 공유하므로 **참고용이며, 처리량·성능 수치가 아님.**

## 측정 한계 (정직한 범위)

- **loopback 측정**: 누수는 애플리케이션 로직(accept/recv/send/close)에서 발생하므로 전송 매체와 무관 → 누수 검증엔 유효. 단 **지연·처리량·최대 수용량 같은 성능 지표는 이 측정으로 말하지 않음**(전용 측정 환경이 따로 필요).
- **2시간 기준**: 더 느린 누수(시간당 수MB)나 시간 기반 버그는 2시간으론 못 잡음. "2h 기준 미관측"으로 한정.
- **변조 5% 포함**: 순수 정상 트래픽이 아니라 비정상 종료 경로가 섞임(누수 관점에선 더 가혹한 조건이지만, 순수 운영값과는 다름).
- **단일 머신**: 서버·부하기 CPU 경합으로 CPU 수치는 참고용.
- **동접 변동**: 800~1,500 출렁여 "1,000"은 평균/피크 기준.

---

세 측정 모두 같은 결론을 가리킵니다. 2시간·51만 사이클 부하에서 메모리·자원 누수는 관측되지 않았습니다. 측정 원본 데이터(perfmon CSV, CRT 힙 출력)는 같은 폴더에 함께 두어 누구든 재현·검증할 수 있게 했습니다.
